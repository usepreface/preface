# Storage and consistency

`packages/database` owns PostgreSQL, Drizzle, migrations, transaction context and
repositories. Its aggregate `DatabaseRepository` exposes `instance`, `auth`, `organization`,
`audit` and `jobs.email`. Repositories decode storage rows with protocol models and accept focused
write schemas; they do not authorize business actors or deliver HTTP responses.

Tables use singular SQL names and UUIDv7 identities generated by the shared UUID
function. Application defaults do not generate IDs for arbitrary direct SQL writers.
Foreign keys preserve user/grant/session history through restrictive deletion.
Organization child references use composite foreign keys with `organizationId`.
See [organization authority](../identity-access/organizations.md) for lifecycle and delegation.
Relations are split into domain `defineRelationsPart` modules and composed after a
schema-wide inference part; tables without explicit relations remain queryable.

Email state changes join ambient transactions. Claim transactions use `SKIP LOCKED`,
then delivery happens outside SQL locks. Lease-owned updates prevent stale workers
from replacing a newer outcome. See [email delivery](../integrations/email.md) for
encryption, expiry, provider differences and recovery limits.

Installation token metadata is either complete or absent and is cleared on completion.
Settings updates require the expected revision and increment it atomically. Owner
mutations serialize on installation; active-grant uniqueness and last-owner protection
preserve an owner while retaining revoked history. An owner grant alone does not
establish that its user is enabled or authorized for a future content operation.

Active canonical emails are trimmed/lowercase and unique; removed address history is retained.
A partial unique index permits one active primary email per user. Composite foreign
keys keep authentication evidence and verification sources on the same user.
`auth.user` owns identity independently of email; `findProfileById` joins the current
primary address for a safe actor projection. Persistence expects already
canonical values; application-input decoding owns normalization. Credential digests/HMACs
are generated by the shared crypto services. Session activity and
revocation updates preserve lifecycle ordering and cannot revive an invalid session.

## Shared transaction context

`Database.layer` acquires one scoped Effect SQL PostgreSQL pool and typed Drizzle
database. Repositories and `TransactionService` share it. Repository queries observe
the ambient Effect SQL transaction even when their service captured the database
at construction. Public repository APIs never accept raw transaction clients.

`TransactionService.run` starts an outer transaction or joins the active one.
Nested calls deliberately introduce no savepoint. Success commits; failures,
defects and interruption roll back. Catching an inner failure inside the outer
transaction can therefore commit earlier writes. Recover outside the transaction
when the whole operation must fail. No automatic transaction retries are installed.

State transitions and required audit writes share a transaction. Remote work and
external email delivery stay outside locks. Lifecycle timestamps use the same Effect clock;
do not mix deterministic application time with later database insertion defaults.

## Migrations and failures

Production migrations use a transaction advisory lock on the reserved migration
connection, with automatic release on completion/failure. They reject execution
inside an existing transaction. The migration Layer completes before application
acquisition and listener startup. Migration files ship as runtime assets and resolve
relative to the source or built module. The development history is one regenerated initial
baseline containing metadata, teams and scoped invitation assignments. Databases using
any deleted development history need an explicit reset; no upgrade/backfill is supplied.
Startup never resets a database. The Google migration adds external identities, source-specific
evidence and email reauthentication to that baseline.

Known SQL/Drizzle errors become `DatabaseError` with structured reasons and retryability.
Internal causes may contain SQL or parameters; public error encoding and routine
logs must not serialize them. The application maps only known semantic constraints;
the server translates operational failures without exposing native causes.

## Audit and verification

Audit correlates event kinds with typed target identities and safe metadata. User
actors require an acting user; system actors carry none. Required setup and session
events are appended by application workflows, not implicitly by repository mutations.
Audit has an append-only repository API; database immutability triggers/privilege
policies are not installed. It is distinct from request logs and aggregate metrics.

PGlite runs real migrations and repositories for fast lifecycle/rollback tests.
Disposable PostgreSQL verifies the driver, locking and concurrency behavior. Its
explicit test configuration cannot fall back to a deployment database. Built smoke
tests verify default exports and packaged migration assets.
